# ChatPlatform — scalable modular monolith

## Decision
Retain ASP.NET Core, the current tenant model, API contracts, adapters, bot engine, durable inbox/outbox and existing UI. Do not rewrite or split into independently deployed microservices by default. Evolve module boundaries in place, and separate API and worker processes from the same release image only when shared storage and concurrency tests permit it.

## Current baseline and limitations
The Fly configuration uses a local SQLite file and a mounted volume with one shared CPU and 512 MB memory. This is a development/small-installation baseline, not proof of capacity for thousands of tenants. Never run several independent SQLite volumes behind a load balancer as though they were one database. The local event bus and process-local rate limits are not distributed guarantees. Inbox revision streaming queries the database regularly. The bot and campaign limits are intentionally bounded. Meta has independent account, permission, throughput, consent and billing constraints.

## Proposed acceptance workload (not measured capacity)
- Ultimate product target: register, link and administer 1,000,000 institutions. The 5,000-institution workload below is the first intermediate gate, not the final target. Separately qualify 1M directory records, 100k and 1M end-to-end provisioning and account mappings in isolated staging. Load assumptions for active institutions, connected accounts, concurrent sessions and events/s must be agreed and measured; registered institutions are not simultaneous users. A million registrations does not imply a million Meta-approved accounts or unlimited Meta throughput. Keep the existing architecture and external adapters; no internal storage migration or splitting without explicit approval.
- 5,000 provisioned institutions; 1,000 active in a representative day; 500 simultaneous authenticated sessions; 2 WhatsApp accounts per active tenant.
- Initial synthetic test: 50 inbound events/s and 50 outbound jobs/s aggregate for one hour, then a five-minute 3x burst; use mocked Graph, no real recipients. Also test a sustained 24-hour mixed workload, highly skewed tenant traffic, revoked credentials, and account throttling.
- Candidate SLOs under that workload: p95 ordinary API latency < 500 ms, p95 durable webhook acknowledgment < 1 s, p95 ready inbox processing < 5 s (excluding upstream delay), no lost accepted events, no cross-tenant data, no automatic duplicate dispatch on ambiguous upstream results. Record CPU, memory, DB locks, queue lag, error rates, and measured limits. Adjust sizing to evidence, not institution count alone.
- Restore a verified backup to staging, compare record counts/checksums and encrypted-token readability, and exercise migration rollback/recovery and rolling version compatibility. Set agreed recovery objectives before commercial launch.

## Incremental stages
1. Shared state: durable single-use signup correlation through a storage interface (implemented candidate in PR #18). Store only hashes, tenant, app/config and expiry. Keep existing SQLite default. Current SQLite CI uses independent contexts; cross-host operation is NOT yet qualified.
2. Database boundary: preserve the existing platform database and add independent external provider adapters (IDatabaseAdapter). Improve existing indexes and pagination only as separately approved capacity work. Internal provider migration or sharding is out of scope unless explicitly authorized.
3. Workload separation: same modular application and image, independent API and messaging worker roles; database leases/fencing, per-account ordering, fair scheduling, ambiguous-send policy, backpressure and distributed rate limits. Verify simultaneous workers, termination/restart, replay, and noisy-neighbor isolation. Use a durable shared event mechanism instead of relying on process-local event notifications.
4. Live updates: bounded connections, shared tenant revision notifications with recovery after reconnect, eliminate per-connection polling amplification, protect session revocation and cross-origin access.
5. Bot and channel extensions: explicit typed node handler and connector contracts, versioned immutable definitions, validated input/output, per-tenant configuration, scoped secrets and bounded execution. Own-model adapter stays optional; no required paid AI provider. External actions are deny-by-default, audited and idempotent.
6. Operations: health/readiness by role, queue depth/age, sanitized structured logs, tracing, per-tenant quotas and capacity dashboards, retention cleanup, encrypted sensitive state and tested backup/restore.
7. Capacity gate: run the synthetic workload and recovery/security scenarios on isolated staging; publish exact image revision, machine sizing and measured results. Increase replicas and resources only with shared storage and validated behavior.

## Multiple databases at the same time
The core PlatformDbContext remains authoritative and its current SQLite provider, schema, module boundaries and routing are not changed by external database integration. Each new database provider is a separate IDatabaseAdapter implementation in Infrastructure/Adapters/Databases, registered by dependency injection. The external registry depends on the contract, not concrete providers. Adding another adapter must not require changes to existing adapters, the core persistence layer, or the bot engine. External databases are a separate tenant-scoped integration plane, keyed by tenant + alias, with independent connections and provider-specific adapters. The initial registry supports SQLite read-only files and a PostgreSQL adapter requiring verified TLS; operator-configured named scalar reads use parameters, never caller-provided SQL. Only connection aliases/provider and connectivity checks are exposed to tenant admins. Query execution is an internal capability, not yet a bot node or public endpoint. A per-process limit of 16 simultaneous operations and disabled external connection pooling are initial guardrails, not distributed quotas. SQL is trusted operator code; use dedicated read-only database roles and separate read-only file mounts, not production credentials. Do not configure untrusted SQL or expose arbitrary SQL to a user or model.
A tenant may have multiple external accounting/ERP sources simultaneously. Internal database splitting, provider migration or sharding is not part of this requirement and must not be introduced without separate explicit approval. Keep cross-store updates asynchronous through durable outbox/events with idempotency, not an assumed atomic transaction. Store routing and credentials independently; require least-privilege accounts, explicit mappings, network allowlists, secret rotation, audited actions and provider-specific integration tests before enabling remote sources. Additional providers (SQL Server/MySQL/Oracle), distributed limits, and explicitly authorized external write operations remain separate work.

## Non-negotiable
Tenant scope comes from authenticated identity or verified channel ownership. No user-supplied tenant override. Maintain existing Meta sandbox configuration and manual linking; no automatic commercial activation. No production deployment, live DB migration, or merge without operator authorization. Passing smoke tests is not a load-test result.

### Initial external connection configuration
Use operator-only secret/environment configuration (example names, not live credentials):
```text
ExternalDatabases__Tenants__tenant-a__accounting__Provider=postgresql
ExternalDatabases__Tenants__tenant-a__accounting__ConnectionName=AccountingA
ExternalDatabases__Tenants__tenant-a__accounting__Reads__lookup=SELECT name FROM customers WHERE customer_id=@input
ConnectionStrings__AccountingA=<secret-provided connection string>
ExternalDatabases__Tenants__tenant-a__warehouse__Provider=sqlite
ExternalDatabases__Tenants__tenant-a__warehouse__ConnectionName=WarehouseA
ConnectionStrings__WarehouseA=Data Source=/external/warehouse.db
```
Both aliases coexist, without changing the existing platform connection. Tenant admins can GET /api/database-connections and POST /api/database-connections/{id}/probe. Only configured IDs/provider and sanitized probe status are returned; credentials and SQL are not returned. Live PostgreSQL connectivity requires a trusted server certificate, network access and a least-privilege role. Do not enable remote sources before verifying egress controls. The SQLite regression tests use distinct disposable database files; PostgreSQL live integration and UI are pending.

## Million-institution administration milestone
The existing SuperAdmin provisioning, subscription, suspension and reset APIs remain in place. The new cursor-based directory reads at most 101 rows per request and supports exact ID, name and administrator username lookup. Additive name/ID index, no table rewrite. Password hashing occurs before the write transaction to reduce lock time. Run `python3 tests/tenant_directory_scale.py 1000000` for an isolated directory/index microbenchmark; this is NOT a full API, concurrent registration, password hashing, worker, Meta, or production capacity test. The existing SQLite volume, local rate limits, worker scheduling, operational limits and Meta approval remain constraints. For future commercial admission, qualify sustained registration with backpressure/idempotency, per-tenant secret/account provisioning, lookup latency, concurrent traffic, failover, recovery, and isolation at the target dataset size. Do not change the primary database architecture without authorization.

### Directory and queue qualification progress
The million-row index benchmark is now part of the isolated CI workflow. The administrator lookup uses a username-indexed subquery to avoid a correlated scan of all institutions. Inbox and outbox claims recheck due/scheduled eligibility at the atomic update and sort equal timestamps by ID. Additive lease indexes support expired-work lookup. Successful outbound status and corresponding tenant-scoped message evidence commit in one transaction. This does not certify fair scheduling, horizontal workers, throughput or all crash/lease recovery cases; those remain qualification requirements.
